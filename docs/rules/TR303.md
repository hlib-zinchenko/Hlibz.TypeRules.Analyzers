# TR303: Type must be immutable

| | |
|---|---|
| Category | Design |
| Default severity | Warning |
| Code fix | Yes, when the change still compiles |

## Cause

A class, struct or record that inherits from or implements a rule set's `match` types can change
after construction, and the rule set sets `require_immutable = true`. One of:

- an instance field isn't `readonly`
- a property has a `set` accessor, of any accessibility
- a field or auto-property stores a mutable collection (`List<T>`, arrays, ...), of any
  accessibility
- a struct isn't a `readonly struct`

## Why

Value objects, domain events, commands and strongly-typed ids are values: two with the same
content are interchangeable, so they can be shared, cached, used as dictionary keys and passed
around without defensive copies. That only holds while nothing can change them. A changed value
object is a new value object: `money.Add(other)` returns a new `Money`.

A `private set` or a private `List<T>` still lets the type's own methods change it, which is why
TR303 goes further than [TR301](TR301.md) and [TR302](TR302.md), which only keep *callers* from
changing an entity directly.

## Configuration

```ini
[*.cs]
typerules.value-objects.match = T:MyApp.Domain.IValueObject
typerules.value-objects.require_immutable = true
```

## How it's checked

- **Instance state the type declares**: explicit fields, and auto-properties through their
  backing fields. Static fields, constants and computed properties are skipped.
- **`init` accessors are fine**: they only run during construction, and positional records use
  them. A positional `record struct` has `set` accessors, which are reported at the parameter;
  a `readonly record struct` doesn't.
- **Mutable collections** are the types [TR302](TR302.md#what-counts-as-mutable) lists. Unlike
  TR302, private ones count too. `IReadOnlyList<T>`, `ImmutableArray<T>` and the like don't.
- **Shallow**: a readonly field of a mutable class type (`private readonly StringBuilder _text`)
  passes. TR303 can't know which of your own types are mutable; match them with a rule set of
  their own to check them too.
- Overrides and explicit interface implementations are skipped: their shape is dictated by what
  they override or implement. Abstract types are checked, since derived types inherit their
  state.

## Example

```csharp
public sealed class Money : IValueObject
{
    private decimal _amount;                      // TR303

    public string Currency { get; private set; }  // TR303
}
```

```
warning TR303: 'Money._amount' is a field that isn't readonly, but rule set 'value-objects' requires immutable types
warning TR303: 'Money.Currency' has a set accessor, but rule set 'value-objects' requires immutable types
```

## Code fix

Each fix breaks any code that still changes the state after construction, so it's applied
speculatively first and **only offered if every document that declares or references the member
still compiles**:

- **Make '...' readonly** adds `readonly` to a field declared on its own (not `int a, b;`).
- **Remove the set accessor** of an auto-property with a `private set`. The constructor can still
  assign a get-only auto-property.
- **Change the set accessor to init** for a wider `set`, so object initializers keep working.
- **Make '...' a readonly struct** adds `readonly` to the struct.

No fix for a mutable collection (the methods that change it need rewriting, e.g. to return a new
instance), or for a `set` accessor with a body.
