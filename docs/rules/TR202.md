# TR202: Type has the wrong equality semantics

| | |
|---|---|
| Category | Design |
| Default severity | Warning |
| Code fix | No |

## Cause

A class, struct or record that inherits from or implements a rule set's `match` types doesn't
compare the way the rule set's `equality` option requires:

- `equality = value`: the type compares by reference. It's a class that isn't a record and
  doesn't override `Equals(object)`, itself or through a base class.
- `equality = identity`: the type is a record, a struct or a record struct. Or it's matched
  through a class (``Entity`1``) and redefines equality itself: it overrides `Equals(object)` or
  implements `IEquatable<T>`.

## Why

Value objects are equal when their values are: two `Money(10, "EUR")` are the same amount. With
reference equality, `Contains`, `Distinct`, dictionary lookups and `==` silently treat them as
different.

Entities are equal when they're the same entity, whatever state each copy holds. A record
compares all its state, so an entity that's a record stops being equal to itself as soon as one
copy changes, and a struct entity is copied on every assignment. An entity's base class
overriding `Equals` to compare ids is fine: that's identity equality. A concrete entity
overriding it again replaces that with whatever it compares, usually its state.

## Configuration

```ini
[*.cs]
typerules.value-objects.match = T:MyApp.Domain.IValueObject
typerules.value-objects.equality = value

typerules.aggregates.match = T:MyApp.Domain.IAggregateRoot
typerules.aggregates.equality = identity
```

`equality` takes `value` or `identity`.

## How it's checked

- **Value equality** is a record (class or struct), a struct, or a class where the type or a base
  class other than `object` overrides `Equals(object)`, such as a `ValueObject` base class
  comparing equality components. Implementing `IEquatable<T>` alone isn't enough: collections
  and `object.Equals` still call `Equals(object)`.
- Plain structs pass `equality = value`: they compare field by field. The runtime's default does
  that through reflection when a field is a reference type, so for hot paths prefer a
  `readonly record struct` or see [CA1815](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca1815).
- A record can only inherit from another record, so an entity matched by a base class
  (``Entity`1``) can't be a record anyway. For those, `equality = identity` checks that no type
  below the matched class overrides `Equals(object)` or implements `IEquatable<T>`: the matched
  class decides how entities compare. Types matched only through an interface may override
  `Equals`, since there's no base class to compare ids for them.
- Abstract types are checked too.
- A type matched by rule sets requiring both gets a diagnostic for the one it doesn't meet.

## Example

```csharp
public sealed class Money : IValueObject { }                // TR202

public sealed record Order(OrderId Id) : IAggregateRoot;    // TR202

public sealed class Customer : Entity<CustomerId>            // TR202 (match T:MyApp.Entity`1)
{
    public override bool Equals(object? obj) => obj is Customer other && other.Name == Name;
}
```

```
warning TR202: 'Money' compares by reference, but rule set 'value-objects' requires value equality
warning TR202: 'Order' is a record, but rule set 'aggregates' requires identity equality
warning TR202: 'Customer' overrides Equals(object), but rule set 'entities' requires identity equality
```

## Code fix

None. Turning a class into a record (or back) changes `with` expressions, deconstruction,
`ToString` and inheritance, and which members an `Equals` override should compare is a design
decision.
