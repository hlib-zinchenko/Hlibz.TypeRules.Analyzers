# TR003: Type must implement its companion interface

| | |
|---|---|
| Category | Design |
| Default severity | Warning |
| Code fix | Yes: generates the interface, or implements an existing one |

## Cause

A non-abstract class, struct or record that implements a rule set's `match` interfaces doesn't
implement its **companion interface**, and the rule set sets `companion_interface = true`.

The companion interface of `GetUserHandler` is `IGetUserHandler`. It must:

- be named `I` + the type's name, with the same number of type parameters (`Lookup<T>` →
  `ILookup<T>`)
- be declared in the same namespace as the type, or the same containing type for a nested type
- extend one of the rule set's matched interfaces, directly or indirectly

## Why

Handlers, endpoints and similar types are often registered in DI by scanning an assembly, and
consumed through a per-type interface: callers depend on `IGetUserHandler` rather than on the
generic `IRequestHandler<GetUser, User>`, and the implementation stays `internal`. The pattern
only works if every implementation has that interface and the interface carries the contract.
TR003 makes a missing one a build error rather than a runtime resolution failure.

## Configuration

```ini
[*.cs]
typerules.handlers.match = T:MyApp.IRequestHandler`2
typerules.handlers.companion_interface = true
```

Every `match` type of a rule set with `companion_interface` must be an interface, since the
companion has to extend one and interfaces can only extend interfaces. A class there is reported
as [TR000](TR000.md).

## Example

```csharp
internal sealed class GetUserHandler : IRequestHandler<GetUser, User> { }   // TR003
```

```
warning TR003: 'GetUserHandler' must implement a companion interface 'IGetUserHandler' that extends 'IRequestHandler<TRequest, TResponse>', as required by rule set 'handlers'
```

## Code fix

**Extract companion interface 'IGetUserHandler'**, when no type of that name exists:

```csharp
// IGetUserHandler.cs (new file, next to GetUserHandler.cs)
public interface IGetUserHandler : IRequestHandler<GetUser, User>;

// GetUserHandler.cs
internal sealed class GetUserHandler : IGetUserHandler { }
```

- The matched interfaces move from the type's base list to the new interface; other base types
  (`IDisposable`, a base class) stay where they are. If the type only gets a matched interface
  through its base class, the interface extends the most specific one it inherits.
- The interface is `public` if everything it extends is public (so it can be consumed from other
  projects), otherwise `internal`. For a nested type, it gets the type's own accessibility.
- The new file uses the same namespace style (file-scoped or block) and line endings as the
  type's file, and only the `using` directives it needs. From C# 12 the interface has no body
  (`interface IFoo : IBar;`), otherwise an empty one.
- Generic and nested types get the interface in their own file, just before the type, because
  their constraint clauses are copied as written and may rely on that file's `using` directives.
  So does any type whose `IFoo.cs` would collide with an existing file.

**Implement 'IGetUserHandler'**, when the interface exists and extends a matched interface, but
the type doesn't implement it: adds it to the base list.

No fix is offered when a type named `IGetUserHandler` exists but isn't an interface, or doesn't
extend a matched interface: renaming or changing it is the author's call.

Fix All (document, project or solution) is supported, including for the generated files.
