# TR007: Type holds a reference to a forbidden type

| | |
|---|---|
| Category | Design |
| Default severity | Warning |
| Code fix | No |

## Cause

A field or auto-property of a type that inherits from or implements a rule set's `match` types
holds a type of a rule set named in its `forbid_member_types`: directly, or inside an array, a
collection or any other generic type.

## Why

In domain-driven design, an aggregate root refers to another aggregate root **by id**, never by
holding it. Holding it blurs the consistency boundary: loading one loads the other, saving one
can change the other, and the two can no longer be split apart. The same shape of rule covers
other boundaries too: DTOs that must not carry entities, read models that must not hold domain
objects.

## Configuration

```ini
[*.cs]
# Aggregate roots don't hold each other.
typerules.aggregates.match = T:MyApp.Domain.IAggregateRoot
typerules.aggregates.forbid_member_types = aggregates

# DTOs don't carry entities. The entities rule set only needs match to be a target.
typerules.dtos.match = T:MyApp.Contracts.IDto
typerules.dtos.forbid_member_types = entities
typerules.entities.match = T:MyApp.Domain.Entity`1
```

`forbid_member_types` takes one or more rule-set names, separated by `|` or `,`, including the
rule set's own name. A rule set named there doesn't need any constraint of its own, only `match`.
Naming a rule set that isn't configured is reported as [TR000](TR000.md).

`allow_self_references` (default `true`) lets a type still hold its own type, e.g. a
`Category.Parent` that is itself a `Category`. Set it to `false` to forbid that too.

## How it's checked

- **Stored state only**: explicit fields of any accessibility (a private `List<Order> _orders` is
  exactly the problem) and auto-properties, including a positional record's properties.
  Computed properties (`public Customer Customer => _customer;`) are skipped, since they store
  nothing and the field they read is checked itself.
- Method parameters, locals and return values are fine: a method that takes another aggregate
  (`order.AssignTo(customer)`) is ordinary DDD.
- The field's type is searched through array elements and type arguments, recursively:
  `Customer?`, `Customer[]`, `List<Customer>`, `Dictionary<Guid, Customer>`, `Lazy<Customer>`
  and `(Customer, int)` all hold a `Customer`.
- A field typed as a matched type itself (`IAggregateRoot _related`) counts too.
- One diagnostic per member, for the first forbidden type found.

## Example

```csharp
public sealed class Order : IAggregateRoot
{
    public Customer Customer { get; private set; }     // TR007
    public CustomerId CustomerId { get; private set; } // fine
}
```

```
warning TR007: 'Order.Customer' holds 'Customer', a type of rule set 'aggregates', which rule set 'aggregates' forbids
```

## Code fix

None. Replacing `Customer` with `CustomerId` also means changing the EF Core mapping, every read
of `order.Customer`, and usually how the two are loaded together: that's a design change, not an
edit.

## Related

[Hlibz.EntityFrameworkCore.ModelRules](https://github.com/hlib-zinchenko/Hlibz.EntityFrameworkCore.ModelRules)
checks the other side of the same boundary: which navigations between aggregates EF Core
actually maps, when the model builds. TR007 reports earlier, while you type, and also covers
state EF doesn't map.
